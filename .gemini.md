# Grit Engineering Standards

> [!IMPORTANT]
> These rules are foundational and must be followed for all Grit development.

## 1. Project Identity
- **Name:** Grit
- **Organization:** hammaadworks
- **Repo:** https://github.com/hammaadworks/grit
- **Core Value:** Maintains a consistent GitHub contribution graph by distributing real work across a timeline.

## 2. Component Architecture (SOLID - Web)
- **Single Responsibility:** Every component must do one thing. If a component grows beyond 100 lines, extract its sub-sections into dedicated files.
- **Atomic Design:** UI primitives (Buttons, Inputs, Cards) live in `src/components/ui`. Feature-specific sections live in `src/components/features`.
- **Reusability:** Never duplicate UI patterns. Extract repeated logic into hooks and shared components.

## 3. Code Quality & Clean Code
- **Explicit Constants:** Use a central `src/lib/constants.ts` for theme colors, URLs, and repeated configuration values.
- **Strict Typing:** Every component prop and function parameter must have an explicit interface or type defined in `src/types`.
- **Meaningful Comments:** Use JSDoc for complex logic. Explain *why*, not just *what*.
- **No "AI Slop":** Avoid bloated inline styles and deeply nested ternary operators. Use `clsx` and `tailwind-merge` for clean class management.

## 4. Library Optimization
- **Tree-shaking:** Ensure imports from `lucide-react` and other libraries are optimized.
- **Performance:** Minimize the use of heavy client-side libraries. Use Framer Motion sparingly for micro-interactions only.

## 5. Documentation & Clarity (Python CLI)
- **Docstrings:** Every public function and class MUST have a PEP 257-compliant docstring explaining its purpose, parameters, and return types.
- **Logic Comments:** Use inline comments to explain the "Why" behind non-trivial logic, such as complex SQL queries or environment detection.
- **Type Hinting:** All Python functions must use explicit type hints for parameters and return values to ensure IDE support and safety.
- **Senior Quality:** Code should read like a premium, production-grade library, not a quick script. Documentation is part of the feature.

## 6. Official Brand Identity (Sacred)
- **Primary Brand Color:** `bright_cyan` (Teal / Bright Blue). This is the core identity.
- **Success Color:** `spring_green3`.
- **Warning Color:** `gold1`.
- **Error/Destructive Color:** `deep_pink3`.
- **Accent/Data Color:** `bright_cyan`. NEVER use purple or other colors that deviate from the core teal identity.
- **Consistency Rule:** All UI components (borders, progress bars, highlights) must use the colors defined above. Any change to brand colors without explicit user approval is strictly prohibited.
